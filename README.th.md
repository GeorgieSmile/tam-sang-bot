# tam-sang-bot

> [English](README.md)

ผู้ช่วย AI รับออเดอร์ทาง LINE พร้อมหน้าจอครัวแบบหน้าเดียวสำหรับร้านอาหารตามสั่ง

ช่วงเวลาเร่งด่วน เจ้าของร้านติดทำอาหารจนตอบแชท LINE ไม่ทัน ส่วนช่วงเวลาปกติก็ยังต้องคอยตอบคำถามซ้ำ ๆ ("เปิดยัง", "หมูกรอบหมดยัง", "กี่บาท") มานั่งแกะแชทบวกราคาเอง และไล่เช็คสลิปโอนเงิน `tam-sang-bot` ช่วยตอบลูกค้าทันที แปลงข้อความสั่งอาหารภาษาไทยที่ไม่เป็นทางการเป็นใบออเดอร์ที่คิดราคาจากโค้ด ตรวจสลิปให้อัตโนมัติ และทำงานร่วมกับ LINE ที่เจ้าของร้านใช้อยู่แล้วโดยแทบไม่ต้องปรับตัว

---

## การทำงานของระบบ

1. **ฝั่งลูกค้า (LINE OA):** พิมพ์สั่งภาษาไทยตามปกติ (ภาษาพูด คำย่อ พิมพ์ผิด สั่งหลายกล่อง หรือส่งพิกัด LINE) บอทตอบเรื่องเปิด/ปิดร้าน ที่อยู่ร้าน เมนู ราคา และของหมดทันที ถ้าลูกค้าถาม "มีเมนูอะไรบ้าง" บอทส่งรายการเมนูครบพร้อมเนื้อสัตว์ที่เลือกได้และราคาที่บวกเพิ่ม ถามเพิ่มเฉพาะจุดที่กำกวมจริง แล้วส่ง **LINE Flex card** สรุปรายการ ราคาที่คำนวณจากโค้ด และเวลารอตอนนี้ (`ตอนนี้รอประมาณ 10–15 นาที`) เมื่อลูกค้ากด **ยืนยันออเดอร์** ออเดอร์จะเข้าคิวครัวทันที ถ้ากด **ยกเลิก** รายการอาหารจะถูกล้าง แต่ระบบยังจำว่ารับเองหรือให้ส่ง ที่อยู่ พิกัด และเวลาที่ขอไว้ ลูกค้าจึงสั่งใหม่ได้เร็ว
   - **ใบยืนยันออเดอร์:** บอกลำดับคิวและเวลารอ (`คิวที่ 2 · ประมาณ 10–15 นาที`) พร้อม **QR พร้อมเพย์ที่ใส่ยอดเงินไว้แล้ว** ถ้าลูกค้ายังค้างจ่ายออเดอร์ก่อนหน้า QR จะเป็นยอดค้างทั้งหมด และใบยืนยันจะแยกรายการแต่ละออเดอร์ให้เห็น
   - **จ่ายเงินสด:** ถ้าลูกค้าบอกว่าจะจ่ายสด ใบยืนยันจะขึ้นว่า `ชำระเงินสด X฿ ตอนรับอาหารได้เลยค่ะ` และไม่ส่ง QR ยกเว้นลูกค้าขอเอง
   - **สลิป:** เมื่อลูกค้าส่งสลิปโอนเงิน บอทอ่าน QR บนสลิป ตรวจกับ [SlipOK](https://slipok.com/) แล้วบันทึกว่าออเดอร์ที่ยอดตรงจ่ายแล้ว (`ได้รับยอด 60฿ แล้วค่ะ ✅ (#3)`) ถ้าลูกค้าส่งสลิปก่อนกดยืนยัน ระบบจะยืนยันออเดอร์ที่เปิดค้างไว้ให้ด้วย สลิปซ้ำ ยอดไม่ตรง โอนผิดบัญชี หรือตรวจไม่ได้ จะส่งต่อให้เจ้าของร้านดู บอทไม่บอกลูกค้าว่าสลิปปลอม
   - **ถามสถานะ:** ถ้าถาม "เสร็จยัง" บอทตอบลำดับคิวและเวลารอ (`ยังไม่เสร็จค่ะ ก่อนหน้าอีก 2 คิว ประมาณ 10–15 นาที`) ถ้าส่งข้อความเสียง บอทตอบว่า `รบกวนพิมพ์เป็นข้อความนะคะ 🙏`
2. **ฝั่งเจ้าของร้าน (สั่งงานผ่านแชท LINE):** พิมพ์ภาษาไทยส่งมาที่ LINE OA เดียวกันจากบัญชี `OWNER_LINE_USER_ID` ไม่ต้องเปิดหลังบ้านหรือจำรหัสผ่าน

   | คำสั่งที่พิมพ์ | ผลลัพธ์ |
   |---|---|
   | `หมูกรอบหมด` / `ข้าวไข่เจียวหมด` | ปิดวัตถุดิบนั้นในทุกเมนูที่ใช้ หรือปิดเฉพาะเมนูที่ระบุ |
   | `หมูกรอบมาแล้ว` / `เปิดครบ` | กลับมาเปิดขายรายการนั้น หรือล้างสถานะของหมดทั้งหมด |
   | `ยุ่ง 25 นาที` / `ยุ่ง` / `โหมดปกติ` | ตั้งเวลารอขั้นต่ำของวันนี้ (5–180 นาที; ถ้าไม่ระบุใช้ 20 นาที) หรือยกเลิก เวลารอที่แจ้งลูกค้าจะไม่ต่ำกว่านี้ และเพิ่มขึ้นตามคิวจริง |
   | `ปิดร้าน` / `เปิดร้าน` | ปิดหรือเปิดรับออเดอร์เฉพาะวันนี้ (หลังเที่ยงคืนกลับไปใช้เวลาเปิด-ปิดปกติ) |
   | `คิว` / `สรุปวันนี้` | ดูจำนวนคิวที่รอทำพร้อมลิงก์ `/kitchen` หรือสรุปออเดอร์และยอดขายวันนี้ ยอดที่จ่ายด้วยสลิปและเงินสด ออเดอร์ที่ยังไม่จ่าย ยอดค้างจากวันก่อน และรายการที่ต้องคืนเงิน |
   | `เปิดแจ้งเตือน` / `ปิดแจ้งเตือน` | เปิด/ปิดการส่ง LINE push แจ้งเจ้าของร้านทุกครั้งที่มีออเดอร์ใหม่ (สำหรับร้านที่ใช้มือถือเครื่องเดียว) |
   | `หยุดบอท` / `เปิดบอท` | หยุดหรือเปิดการตอบลูกค้าอัตโนมัติชั่วคราว (รวมถึงการตรวจสลิป) |

   ถ้าบัญชีเจ้าของร้านพิมพ์ข้อความอื่นที่ไม่ตรงคำสั่ง บอทจะตอบรายการคำสั่งทั้งหมดกลับไป

3. **หน้าจอครัว (`/kitchen`):** หน้าเว็บเดียวสำหรับเปิดบนมือถือหรือแท็บเล็ตข้างเตา
   - **คิว:** เรียงตามเวลา (ออเดอร์ค้างจากวันก่อนขึ้นก่อน พร้อมป้าย `เมื่อวาน`) เน้นหมายเหตุสำคัญ (`ไม่ใส่ผัก`, `แยกน้ำ`) มีลิงก์ `เปิดแผนที่` สำหรับลูกค้าที่ปักหมุด และปุ่ม `ทำเสร็จแล้ว`, `เสร็จ + แจ้งลูกค้า`, `ยกเลิก` บนมือถือ การ์ดจะย่อเหลือเลขคิว เวลา รายการ และป้าย แตะเพื่อดูรายละเอียด
   - **การจ่ายเงิน:** ทุกออเดอร์มีป้ายสถานะ (`ยังไม่จ่าย`, `จะจ่ายสด`, `💵 เงินสด`, `โอนแล้ว (ร้านเช็ค)`, `โอนแล้ว (สลิป) ✅`) มีปุ่ม **รับเงินสดแล้ว** / **รับโอนแล้ว** / **ยกเลิกจ่าย** ตอนกดเสร็จออเดอร์ที่ยังไม่จ่าย ระบบจะถามว่ารับเงินสดแล้วหรือยัง และมีส่วน **ค้างจ่าย** รวมออเดอร์ที่ทำเสร็จแล้วแต่ยังไม่จ่ายจากทุกวัน
   - **ลูกค้ารอตอบ (inbox):** การ์ดของแชทที่ต้องให้คนตอบ เช่น สลิปมีปัญหา ส่งรูป ถามส่วนผสมหรือแพ้อาหาร ขอแก้ออเดอร์ที่ยืนยันแล้ว ขอยกเลิกออเดอร์ที่จ่ายแล้ว หรือคุยเกิน 30 ข้อความในวันนี้ การ์ดบอกเหตุผล ข้อความล่าสุดของลูกค้า และเวลาที่บอทจะพักอีกกี่นาที มีเสียงเตือนแยกจากออเดอร์ใหม่ และส่ง LINE push แจ้งเจ้าของร้านได้
   - **รวมจาน:** รวมเมนูที่เหมือนกันในคิวไว้ด้วยกันเพื่อทำทีเดียว พร้อมหมายเหตุของแต่ละออเดอร์
   - **แถบด้านบน:** ปุ่มเปิด/ปิดร้าน โหมดยุ่ง ของหมด สวิตช์แจ้งเตือน LINE สองตัว (`LINE ออเดอร์ใหม่`, `LINE ลูกค้ารอตอบ`) คำเตือนเมื่อโควตา SlipOK ใกล้หมด เสียงเตือนออเดอร์ใหม่ และกันหน้าจอดับ (Screen Wake Lock)

## ส่งต่อให้เจ้าของร้าน และช่วงที่บอทพัก

ถ้าแชทไหนต้องให้เจ้าของร้านตอบ บอทจะตอบครั้งเดียว (`ส่งข้อความให้ร้านแล้วค่ะ เดี๋ยวร้านตอบกลับนะคะ`) เปิดการ์ดใน inbox แล้ว**พักการตอบลูกค้าคนนั้น** เจ้าของร้านตอบในแอป LINE OA ตามปกติ หรือจะกด **คุยเอง** ที่ออเดอร์ในคิวหรือแถวค้างจ่ายเพื่อรับแชทเองก็ได้ โดยบอทไม่ส่งอะไรให้ลูกค้า

ระหว่างพัก บอทไม่ตอบและไม่เรียก LLM สำหรับลูกค้าคนนั้น ข้อความที่ลูกค้าส่งมาจะถูกบันทึกและขึ้นบนการ์ด บอทกลับมาตอบเองเมื่อลูกค้าเงียบครบ **15 นาที** เมื่อลูกค้ากดยืนยัน/ยกเลิกออเดอร์ เมื่อขึ้นวันใหม่ หรือเมื่อเจ้าของร้านกด **ให้บอทตอบต่อ** ส่วนแชทที่เกิน 30 ข้อความต่อวัน บอทจะกลับมาเฉพาะเมื่อกดปุ่มนี้หรือขึ้นวันใหม่ ตอนกลับมา บอทรู้ว่าร้านคุยเรื่องก่อนหน้าไปแล้ว จึงไม่ตอบคำถามเดิมซ้ำ

## แนวคิดหลักในการออกแบบ

- **โค้ดคุมราคา การจ่ายเงิน และกติกาทั้งหมด:** LLM ทำหน้าที่เข้าใจภาษาไทยและเลือกเรียก tool เท่านั้น ส่วนราคา ตัวเลือกที่สั่งได้ ของหมด ค่าส่ง รายการเมนู การจับคู่สลิป และเวลารอ คำนวณจาก `menu.yaml` และ SQLite ในโค้ด
- **บันทึกการจ่ายเงิน แต่ไม่บังคับจ่ายก่อน:** ออเดอร์ที่ยืนยันแล้วเข้าคิวทำทันทีไม่ว่าจะจ่ายหรือยัง ลูกค้าจ่ายก่อน ระหว่าง หรือหลังทำอาหารก็ได้ หรือจ่ายวันหลังก็ได้ ([ADR-0001](docs/adr/0001-payments-tracked-not-gated.md)) สลิปหนึ่งใบจ่ายออเดอร์ที่ค้างเก่าสุดที่ยอดรวมตรงกับยอดสลิปพอดี ไม่แบ่งยอดสลิป และใช้ได้ครั้งเดียว
- **ใช้ LINE push น้อย:** การตอบแชท ใบยืนยันออเดอร์ QR และผลตรวจสลิปใช้ `reply` token ซึ่งฟรีไม่จำกัด โควตา push (300 ข้อความ/เดือนในแพ็กเกจฟรี) ใช้เฉพาะตอนเจ้าของร้านกดยกเลิก กด `เสร็จ + แจ้งลูกค้า` และแจ้งเตือนเจ้าของร้าน คือออเดอร์ใหม่ (ปิดไว้เป็นค่าเริ่มต้น) และการ์ดลูกค้ารอตอบใบใหม่ (เปิดไว้เป็นค่าเริ่มต้น)
- **ลดการถามจุกจิกและไม่พูดแทรกเจ้าของร้าน:** ถ้าลูกค้าไม่ได้ระบุ ระบบใช้ค่าเริ่มต้น `เผ็ดปกติ` / `หวานปกติ` อัตโนมัติ จำที่อยู่และพิกัดเดิมของลูกค้าที่เคยสั่งส่ง ตอบคำทักทายแล้วถามว่าจะรับอะไร ถ้าลูกค้าถามเมนูที่ร้านไม่มี บอทแนะนำเมนูใกล้เคียงให้ และส่งต่อให้เจ้าของร้านตอบเอง (`hand_over`) เมื่อถามเรื่องส่วนผสมหรือแพ้อาหาร หรือขอแก้ออเดอร์ที่ยืนยันแล้ว
- **ไม่ตอบทับเจ้าของร้าน:** ก่อนส่งข้อความทุกครั้ง บอทเช็คอีกรอบว่ายังไม่ได้ถูกพัก ถ้าเจ้าของร้านกด **คุยเอง** ระหว่างที่บอทกำลังตอบ บอทจะไม่ส่งข้อความนั้น
- **สั่งจบในข้อความเดียวได้เร็วขึ้น:** ถ้าลูกค้าบอกออเดอร์ครบในข้อความเดียว บอทส่งการ์ดออเดอร์พร้อมข้อความสำเร็จรูป โดยไม่เรียก LLM รอบที่สอง เร็วขึ้นประมาณ 1.1 วินาที (4.35 → 3.23 วินาทีบน Haiku) ถ้าข้อความมีคำถาม เช่น "ไหม" หรือ "ตรงไหน" หรือขอข้อมูลร้าน เช่น "ขอที่อยู่ร้านหน่อย" บอทยังเรียก LLM รอบที่สองตามเดิม เพื่อไม่ให้คำถามแทรกตกหล่น ([ADR-0002](docs/adr/0002-card-fast-path-question-word-check.md))
- **log ไม่เก็บข้อมูลส่วนตัว:** บันทึกหนึ่งบรรทัดต่อการเรียก LLM และต่อ LINE event หนึ่งครั้ง มีเวลาที่ใช้ จำนวน token และ cache hit แต่ไม่บันทึกข้อความลูกค้า ที่อยู่ หรือ LINE user ID
- **เทคโนโลยีพอดีกับงาน:** Python 3.13, FastAPI, SQLite (WAL), `httpx`, `zxing-cpp` + `Pillow` (อ่าน QR บนสลิป), `segno` (สร้าง QR พร้อมเพย์) และ OpenAI SDK ที่เปลี่ยนผู้ให้บริการหรือโมเดลได้ผ่าน `.env` (ค่าเริ่มต้นเป็น OpenRouter)

## ผลการทดสอบ (evaluation)

โปรเจกต์นี้ยังไม่มีร้านจริง ตัวเลขด้านล่างจึงมาจากการทดสอบแบบ offline (27 พ.ย. 2026) ไม่ได้มาจากลูกค้าจริง วิธีทดสอบอยู่ใน [สเปกการทดสอบ](docs/specs/2026-11-27-order-eval.md) ผลดิบอยู่ใน [`evals/results/`](evals/results/)

**ความแม่นยำในการรับออเดอร์:** ใช้แชทจำลอง 80 แชทในภาษา LINE แบบที่ลูกค้าพิมพ์จริง (พิมพ์ผิด ภาษาพูด สั่งหลายจาน ถามเรื่องอื่นแทรก และข้อความที่ไม่ใช่การสั่ง) ให้โมเดลจากค่ายอื่นเป็นคนเขียน โมเดลที่ถูกทดสอบจึงไม่ได้เขียนข้อสอบเอง GPT-6.2 Sol เขียน 40 แชท ([`gpt.yaml`](evals/cases/gpt.yaml)) และ Gemini 4 Neon เขียน 40 แชท ([`gemini.yaml`](evals/cases/gemini.yaml)) ผู้เขียนทั้งสองไม่เห็นโค้ด prompt หรือ test และชุดของ Gemini ถูกเก็บไว้ไม่เปิดอ่านจนถึงรอบสุดท้าย แต่ละแชทรันผ่านแอปจริง (LINE และ SlipOK เป็น stub ส่วน LLM เป็นของจริง) แล้วให้โค้ดตรวจผลจากฐานข้อมูล คือรายการในการ์ดออเดอร์ ตัวเลือก จำนวน และรับเองหรือให้ส่ง หรือการส่งต่อให้เจ้าของร้าน ไม่ใช้ LLM เป็นคนตัดสิน รันแชทละ 3 รอบ ด้วย reasoning effort ระดับ low

| โมเดล | ผ่าน (80 แชท × 3) | ชุด GPT | ชุด Gemini (ชุดซ่อน) | เวลาตอบ (มัธยฐาน) | เวลาตอบ (p95) | ค่าใช้จ่ายต่อแชท |
|---|---|---|---|---|---|---|
| Claude Haiku 5.5 (ค่าเริ่มต้น) | 236/240 (98.3%) | 99.2% | 97.5% | 2.95 วินาที | 4.8 วินาที | $0.00058 |
| Claude Sonnet 5.5 | 237/240 (98.75%) | 100% | 97.5% | 2.0 วินาที | 4.0 วินาที | $0.0074 |

Sonnet แพงกว่าประมาณ 13 เท่าแต่ผ่านเพิ่มแค่ 1 รอบ จึงยังใช้ Haiku เป็นค่าเริ่มต้น เวลาตอบคือเวลาที่บอทใช้ต่อ LINE event หนึ่งครั้ง (`total_ms` ใน log) ค่าใช้จ่ายเป็นค่าสูงสุด เพราะคิด input ที่ไม่ได้ cache ด้วยราคาที่สูงกว่าระหว่างราคา input กับราคา cache write

**ลูกค้าจำลอง:** ให้ Gemini 4 Hydrogen สวมบทลูกค้า 20 คน แต่ละคนมีบุคลิกและออเดอร์ในใจที่บอทไม่รู้ ([`goals.yaml`](evals/goals.yaml)) คนละ 3 รอบ ตามแนวทางของ τ-bench ลูกค้าจะจบแชทเมื่อการ์ดออเดอร์ตรงกับที่ต้องการ หรือเมื่อลูกค้าพิมพ์ครบ 8 ข้อความ แล้วตรวจผลแบบเดียวกัน ได้ pass^1 98.3% (ผ่าน 59 จาก 60 แชท) และ pass^3 95% (ลูกค้า 19 จาก 20 คนสั่งสำเร็จครบทั้ง 3 รอบ) แชทเดียวที่ไม่ผ่านเกิดจากลูกค้าจำลองจบแชทเร็วเกินไป ไม่ใช่ความผิดของบอท

**สิ่งที่การทดสอบเจอ:** ในชุดซ่อน ข้อความแรกที่ขอข้อมูลโดยไม่มีคำถาม ("ขอที่อยู่ร้านหน่อยค่ะ") ไม่ได้รับคำตอบเลยทั้ง 3 รอบในทั้งสองโมเดล เพราะ fast path ข้าม LLM รอบที่สอง หลังแก้ ([ADR-0002](docs/adr/0002-card-fast-path-question-word-check.md)) ผ่านครบ 3 รอบ รอบหลังจากนั้นที่รันกับชุดเดิมได้ 238–239/240 แต่ตอนนั้นรู้จักแชทชุดนี้แล้ว จึงไม่นับเป็นการทดสอบใหม่

**รันเอง** (เสียเงิน ใช้โมเดลตามที่ตั้งไว้ใน `.env`):

```bash
uv run python scripts/eval.py run --set dev --runs 3 --max-cost-usd 0.5
uv run python scripts/eval.py simulate --simulator google/gemini-4-hydrogen --runs 3 --max-cost-usd 1.0
```

## เริ่มต้นใช้งาน (รันในเครื่อง + ต่อ LINE OA จริง)

**สิ่งที่ต้องมี:** [`uv`](https://docs.astral.sh/uv/) (ติดตั้ง Python 3.13 ให้เองตามที่ระบุใน `.python-version`), คำสั่ง `sqlite3` (สำหรับสคริปต์ช่วยทดสอบ), บัญชี LINE Official Account ที่เปิด Messaging API แล้ว, API key ของ OpenRouter (หรือผู้ให้บริการที่รองรับ OpenAI API) และ `cloudflared` (`brew install cloudflared`) สำหรับเปิด HTTPS tunnel ตอนทดสอบในเครื่อง ถ้าต้องการ: เลขพร้อมเพย์ (สำหรับ QR) และบัญชี [SlipOK](https://slipok.com/) (สำหรับตรวจสลิป)

1. **ติดตั้ง dependency:**
   ```bash
   uv sync --locked
   ```
2. **สร้างไฟล์ `.env`:**
   ```bash
   cp .env.example .env
   ```
   กรอกค่าหลักใน `.env` *(ค่าที่ export ใน shell จะถูกใช้ก่อนค่าใน `.env`)*:
   - `KITCHEN_SECRET` — เปลี่ยนจาก `change-me-kitchen-secret` เป็นคีย์สุ่มสำหรับเปิดหน้า `/kitchen` (เช่น `openssl rand -hex 24`)
   - `LINE_CHANNEL_SECRET` และ `LINE_CHANNEL_ACCESS_TOKEN` — จาก LINE Developers Console
   - `OWNER_LINE_USER_ID` — รหัส `U...` จาก **LINE Developers Console → ช่องของคุณ → Basic settings → Your user ID** *(หรือเว้นว่างไว้ก่อนแล้วค่อยดึงในขั้นตอนที่ 5)*
   - `LLM_API_KEY` — API key ของ OpenRouter (หรือปรับ `LLM_BASE_URL` / `LLM_MODEL` ตามผู้ให้บริการที่ใช้)
   - `PROMPTPAY_ID` *(ไม่บังคับ)* — เบอร์โทร 10 หลักหรือเลขประจำตัว 13 หลัก ใบยืนยันออเดอร์จะมี QR พร้อมเพย์ที่ใส่ยอดเงินไว้แล้ว ถ้าเว้นว่างจะไม่มี QR
   - `PAYMENT_INFO_TEXT` *(ไม่บังคับ)* — ข้อความเลขพร้อมเพย์/บัญชีแบบบรรทัดเดียว แสดงบนใบยืนยันออเดอร์เมื่อไม่ได้ตั้ง `PROMPTPAY_ID`
   - `SLIPOK_API_KEY` และ `SLIPOK_BRANCH_ID` *(ไม่บังคับ ต้องใส่ทั้งคู่หรือเว้นทั้งคู่)* — จากบัญชี SlipOK โดย branch ID เป็นตัวเลข ถ้าไม่ใช่ตัวเลข แอปจะไม่ยอมเริ่มทำงาน (มักแปลว่าใส่สองค่านี้สลับกัน) ต้องลงทะเบียนบัญชีธนาคารเดียวกับ `PROMPTPAY_ID` ในการตั้งค่า LINE ของ SlipOK ไม่อย่างนั้นทุกสลิปจะไม่ผ่านการเช็คบัญชีผู้รับ ถ้าเว้นทั้งคู่ สลิปจะเข้า inbox ให้เจ้าของร้านตรวจเอง
3. **เปิดเซิร์ฟเวอร์และ tunnel:**
   ```bash
   ./scripts/dev.sh run
   ```
   เปิดอีกเทอร์มินัลแล้วรัน:
   ```bash
   cloudflared tunnel --url http://127.0.0.1:8000
   ```
   *(Quick tunnel ของ `cloudflared` จะเปลี่ยน URL ทุกครั้งที่รีสตาร์ต ต้องอัปเดต Webhook URL ใน LINE และ `PUBLIC_BASE_URL` ใหม่ทุกครั้ง หรือใช้ named tunnel แทน)*
4. **ตั้งค่า LINE OA และ `PUBLIC_BASE_URL`:**
   - ใน **LINE Developers Console → Messaging API** ใส่ Webhook URL เป็น `https://<tunnel-url>/line/webhook` กด **Verify** แล้วเปิด **Use webhook**
   - ใน **LINE OA Manager → Response settings** ปิด **Auto-reply messages** (เปิด **Chat** ไว้ตามเดิมเพื่อให้เจ้าของร้านตอบเองได้)
   - ใส่ `PUBLIC_BASE_URL=https://<tunnel-url>` ใน `.env` แล้วรีสตาร์ต `./scripts/dev.sh run` LINE โหลดรูป QR พร้อมเพย์จาก URL HTTPS นี้ และคำสั่ง `คิว` ก็ลิงก์ไปที่นี่ จึงใช้ `localhost` ไม่ได้
5. **ตั้งค่าบัญชีเจ้าของร้านและข้อควรรู้ตอนทดสอบ:**
   - ถ้าเว้น `OWNER_LINE_USER_ID` ไว้ ให้ทัก OA หนึ่งครั้งแล้วรัน `./scripts/dev.sh users` เพื่อดูรหัส `U...` นำไปใส่ใน `.env` แล้วรีสตาร์ต
   - **กรณีทดสอบด้วยมือถือเครื่องเดียว:** ทุกข้อความจาก `OWNER_LINE_USER_ID` จะถูกส่งไปฝั่งคำสั่งเจ้าของร้าน (ถ้าพิมพ์สั่งอาหารจะได้รายการคำสั่งกลับมาแทน) ถ้าอยากทดสอบฝั่งลูกค้า ให้ทักจากบัญชี LINE อื่น หรือเว้น `OWNER_LINE_USER_ID=` ว่างไว้ชั่วคราวแล้วรีสตาร์ต การแจ้งเตือนเจ้าของร้านต้องตั้ง owner ID ไว้ จึงต้องทดสอบด้วยสองบัญชี
6. **เปิดหน้าจอครัว:**
   เข้า `https://<tunnel-url>/kitchen?key=<KITCHEN_SECRET>` บนมือถือหรือแท็บเล็ต (ระบบจะเก็บคีย์ไว้ใน `HttpOnly` cookie ตั้งแต่ครั้งแรกที่เข้า ทำให้รีเฟรชหน้าได้โดยไม่ต้องใส่ `?key=` ซ้ำ และคีย์จะถูกซ่อนใน log ของเซิร์ฟเวอร์) แล้วแตะแถบด้านบนหนึ่งครั้งเพื่อเปิดเสียงเตือนและกันหน้าจอดับ

## ขึ้นระบบจริง (production)

quick tunnel ข้างบนใช้ทดสอบเท่านั้น เพราะ URL เปลี่ยนทุกครั้งที่รีสตาร์ต และบอทหยุดทำงานเมื่อคอมพิวเตอร์ sleep ระบบจริงรันบน VM `e2-micro` ฟรีของ Google Cloud:
- systemd คอยให้แอปทำงานตลอด
- Caddy ให้บริการ HTTPS และต่ออายุใบรับรอง Let's Encrypt ให้เอง
- ชื่อโดเมนจาก DuckDNS ทำให้ webhook ของ LINE มี URL คงที่
- `shop.db` ถูกสำรองไปที่ Cloud Storage ทุกคืน
- โค้ดที่ push เข้า `main` จะ deploy เองเมื่อ CI ผ่านและร้านปิดแล้ว ถ้า health check ไม่ผ่าน ระบบย้อนกลับเวอร์ชันเดิมให้อัตโนมัติ

คำสั่งที่ใช้ประจำ (deploy, rollback, ดู log) วิธีกู้ข้อมูลจาก backup และขั้นตอนสร้างเซิร์ฟเวอร์ใหม่ทั้งหมด อยู่ใน [docs/deploy.md](docs/deploy.md) (ภาษาอังกฤษ)

## ปรับใช้กับร้านจริง

แก้ไฟล์ [menu.yaml](menu.yaml) ได้โดยตรงโดยไม่ต้องทำระบบหลังบ้าน:
- `shop.name`, `shop.hours` (เวลาเปิด-ปิดในโซน `Asia/Bangkok`) และ `shop.delivery` (`fee` และ `free_above`; ถ้าส่งฟรีตั้ง `fee: 0`)
- `shop.address` *(ไม่บังคับ)*: บอทใช้ตอบเมื่อลูกค้าถาม "ร้านอยู่ตรงไหน" ถ้าไม่ใส่ บอทจะไม่มีที่อยู่ให้ตอบ ค่านี้ต้องเป็นข้อความ ไม่อย่างนั้นแอปจะไม่เริ่มทำงาน
- `wait` (`minutes_per_box` และ `min_wait`): เวลารออัตโนมัติ = จำนวนกล่องอาหารจานหลักในคิว × `minutes_per_box` และไม่ต่ำกว่า `min_wait` เมนูเสริมและเครื่องดื่มไม่นับ
- `ingredients`, `option_groups` และ `items` (ราคาตั้งต้น `category`: `meal` / `side` / `drink` เนื้อสัตว์ที่เลือกได้ และชื่อเรียกอื่นที่ลูกค้าใช้) รายการเมนูที่บอทส่งให้ลูกค้าสร้างจากข้อมูลนี้ จึงอัปเดตตามเองโดยอัตโนมัติ

## คำสั่งสำหรับพัฒนาและทดสอบ

```bash
./scripts/check.sh           # ตรวจ format, lint (ruff), type (mypy) และ pytest บรรทัดสุดท้ายบอกผลเสมอ ("check.sh: PASS" หรือ FAIL)
./scripts/dev.sh reset-db    # ล้างออเดอร์ แชท และสลิปทดสอบใน shop.db โดยไม่ต้องหยุด uvicorn
./scripts/dev.sh users       # ดูรายการ LINE userId ที่บันทึกอยู่ใน shop.db
./scripts/dev.sh slips [dir] # อ่าน QR จากรูปสลิปจริง (ค่าเริ่มต้น local/slips/) ไม่เรียก API
./scripts/dev.sh demo        # รันแอปจริงบนฐานข้อมูลทดลองที่ใส่ข้อมูลตัวอย่างไว้ LINE/LLM/SlipOK เป็นของจำลอง (พอร์ต 8765)
./scripts/dev.sh demo-up     # รันเดโมเดียวกันเบื้องหลัง (หยุดด้วย demo-down)
./scripts/dev.sh say U_DEMO slip 70  # ส่ง LINE event จำลองไปที่เดโม แล้วแสดงข้อความที่ LINE จะได้รับ
```

`check.sh` รันอัตโนมัติใน git pre-commit hook และใน CI ด้วย (GitHub Actions บน Ubuntu 24.04 ตรงกับ VM ที่ใช้จริง)

LLM ในเดโมเป็นของจำลองที่ตอบข้อความลูกค้ากลับไปตรง ๆ ถ้าอยากลองสร้างการ์ดออเดอร์โดยไม่เรียก LLM จริง ให้ขึ้นต้นข้อความด้วย `!tools` ตามด้วยชุดคำสั่ง tool แบบ JSON เช่น `!tools [["update_cart", {...}], ["build_order_card", {}]]` ถ้าตั้ง `DEMO_REAL_LLM=1` เดโมจะใช้โมเดลจริงตาม `.env` ซึ่งเสียค่าใช้จ่าย

*(หมายเหตุ: `reset-db` และ `users` ต้องมีฐานข้อมูลที่ถูกสร้างหลังแอปได้รับ request แรกแล้ว ส่วน `users` ต้องมีคำสั่ง `sqlite3` ด้วย ถ้าเปลี่ยน `DB_PATH` ใน `.env` ให้ export `DB_PATH` ใน shell ก่อนรันคำสั่งเหล่านี้ เก็บรูปสลิปจริงไว้ใน `local/` ซึ่ง git ไม่ติดตาม และห้าม commit)*

อัปเกรดจาก v1: ตอนเปิด v2 ครั้งแรก ระบบเพิ่มตารางและคอลัมน์ใหม่ในฐานข้อมูลเดิม และตั้งออเดอร์เก่าทั้งหมดเป็น `legacy` (ก่อนระบบจ่ายเงิน) จึงไม่นับเป็นยอดค้าง ควรสำรอง `shop.db` ไว้ก่อน

ดูรายละเอียดสถาปัตยกรรม โครงสร้างตาราง SQLite และเงื่อนไขทั้งหมดเพิ่มเติมได้ที่ [SPEC.md](SPEC.md) (v2) และ [docs/specs/v1.md](docs/specs/v1.md) (v1)
